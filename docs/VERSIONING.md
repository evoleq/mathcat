# Versioning of MathCat

MathCat uses SemVer-shaped **annotated Git tags** `vX.Y.Z` on `master`. A Git tag is a version checkpoint, **not** a Maven publication or a claim of stable API compatibility.

## Preconditions

Only a successful **CI push run on master** may create a tag. PR CI runs do not tag. If master has advanced during CI, the old run does not tag. No existing tag is overwritten. Tagging uses the exact tested commit SHA and never bypasses checks.

The first tag is `v0.1.0`, reflecting an experimental pre-1.0 library. Subsequent successful master changes advance the version based on Conventional Commit messages since the most recent reachable SemVer tag:

| Change | Before v1.0 | From v1.0 |
| --- | --- | --- |
| `fix:`, `refactor:`, `docs:`, `test:`, `chore:` | patch | patch |
| `feat:` | minor | minor |
| `feat!:`, `fix!:` or `BREAKING CHANGE:` | minor | major |

For a group of commits, the highest-impact category wins. A future `v1.0.0` (and the stability promise it entails) requires an **explicit human decision**, not an automated promotion from `0.x.y`.

Tags are generated by `.github/workflows/semver-tags.yml` on the completed-success event of the existing `CI` workflow and require `contents: write` for that workflow's `GITHUB_TOKEN`. If repository Actions permissions prohibit tag creation, the workflow fails visibly; administrators must adjust permission policy or tags must be created by an authorized maintainer. No release artifacts are published automatically.

## Practical requirements

Write useful Conventional Commit subjects (e.g., `feat(core): ...`, `fix(storage): ...`) for each merged PR. Keep PRs reviewable and tests green before merging. On a release, check that the latest SemVer tag points to the commit tested by the successful master CI run. Do not conflate a successful PR merge with a successful master CI run.

The version applies to the whole repository at present; this is not independent module versioning. Revisit only if the module release lifecycle diverges.
